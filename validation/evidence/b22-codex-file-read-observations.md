# Recovering file-read observations from Codex

Research date: 2026-08-28

Installed desktop runtime: `codex-cli 0.149.0-alpha.4.1`

Newest published CLI checked: `codex-cli 0.150.1`

## Executive conclusion

Codex does not expose an exhaustive, filesystem-observed `FileRead` event in either
the installed ChatGPT desktop build or the newest published CLI. Its Bash hooks carry
the command and result, not a list of files accessed. There is no configuration flag
that switches source inspection to a general built-in `read_file` tool.

There is, however, a better supported source than parsing rollout JSONL or parsing raw
shell strings inside Stickguy:

1. Start a version-matched Codex app-server as a private local child.
2. Discover desktop tasks with `thread/list` and retrieve their persisted items with
   the stable, read-only `thread/read` method.
3. Consume `commandExecution.commandActions`. Codex supplies a structured `read`
   action with `path`, as well as `listFiles`, `search`, and `unknown` variants.

I verified this end to end against the still-running ChatGPT desktop task that produced
this report. A separate instance of the installed app-server returned that task without
resuming or taking ownership of it, and its `commandExecution` items contained
`commandActions: [{"type":"read", ... "path":"..."}]`. The current official
[app-server documentation](https://learn.chatgpt.com/docs/app-server) documents both
`thread/read` and `commandExecution.commandActions`.

This is a supported transport and a vendor-produced parse, but it is not complete read
observation. OpenAI describes command actions as a best-effort understanding of what a
command will do. A controlled compound Bash command in this investigation was classified
as `unknown` even though it read files. Stickguy must therefore store this as
`vendor_inferred` or an equivalent lower-fidelity class, never as exhaustive observed
evidence.

The practical answer is:

- **Supported, passive, structured partial read evidence exists today.** Use the
  app-server read API and `commandActions`.
- **No supported exhaustive read mechanism was found.** No checked surface reports the
  files the process actually opened or read.
- **Do not make rollout JSONL parsing or an independent shell parser the primary
  contract.** They are unnecessary for the main path and materially more fragile.

## Scope and evidence standard

The investigation used official OpenAI documentation, exact schemas generated by the
installed binary, a verified copy of the newest published CLI package, sanitized queries
of the current rollout, and a live read-only app-server test. “Not found” below means the
named official surface, generated schema, feature list, or installed data was checked; it
does not claim that an undocumented private implementation can never exist.

All app-server and rollout inspection stayed on the machine. Raw task content, source,
command strings, command output, environment values, and credentials must remain local
in any product implementation.

## 1. Does Codex expose file reads structurally?

### What exists

The app-server `ThreadItem` union includes:

```text
commandExecution {
  id, command, cwd, status,
  commandActions,
  aggregatedOutput?, exitCode?, durationMs?
}
```

The generated `CommandAction` union in both checked versions is:

```text
read      { command, name, path }
listFiles { command, path? }
search    { command, query?, path? }
unknown   { command }
```

The official documentation identifies `commandExecution` and `commandActions` as part
of the app-server item model, and `item/completed` as the authoritative final item.
It also has an `imageView {id, path}` item, but that covers the image viewer only and is
not a general source-read facility. See [App-server items and events](https://learn.chatgpt.com/docs/app-server#items).

The installed desktop rollout persists the same vendor classification under the private
internal name `parsed_cmd`; its variant spelling is `read`, `list_files`, `search`, or
`unknown`. A simple `sed` read produced a path-bearing `read` action. A representative
compound command containing directory inspection, search, and two file reads produced
`unknown`. That negative case matters: the structure is safer and more maintainable than
Stickguy inventing its own shell grammar, but it still has false negatives.

### What does not exist

No general `FileRead` item, `read_file`/`view_file` tool, or feature/configuration switch
was found in:

- the installed `0.149.0-alpha.4.1` stable and experimental generated app-server schemas;
- the verified `0.150.1` stable and experimental generated schemas;
- either binary's `features list` output;
- the current official [Codex configuration schema](https://learn.chatgpt.com/docs/config-schema.json);
- the `0.149.0` through `0.150.1` entries in the official
  [Codex changelog](https://learn.chatgpt.com/docs/changelog).

The `0.150.0` release adds an `Interrupt` hook, not file-read telemetry. Version `0.150.1`
is a compaction bug-fix release. The `CommandAction` types are identical between the
installed `0.149` build and published `0.150.1`.

The app-server also has client-facing `fs/readFile` and `fs/watch` methods. These do not
report agent activity: `fs/readFile` performs a read requested by the app-server client,
while `fs/watch` emits `fs/changed` after a path changes. The documentation explicitly
describes the watcher as UI invalidation after file or directory changes, not read
tracking. See [App-server filesystem API](https://learn.chatgpt.com/docs/app-server#filesystem).

**Finding:** Codex exposes structured, vendor-inferred read actions, but no structured
record of files actually read by a shell process.

## 2. Hooks: complete installed event and payload surface

The research brief's prose lists ten names while calling them nine; one listed name,
`PostToolUseFailure`, is not supported by the installed runtime and is not configured in
the actual file. `~/.codex/hooks.json` contains these nine configured event keys:

```text
PermissionRequest
PostToolUse
PreToolUse
SessionEnd
SessionStart
Stop
SubagentStart
SubagentStop
UserPromptSubmit
```

The installed `0.149.0-alpha.4.1` binary supports eleven hook events. The two supported
but unconfigured events are `PreCompact` and `PostCompact`. Exact generated type:

```text
preToolUse | permissionRequest | postToolUse | preCompact | postCompact |
sessionStart | sessionEnd | userPromptSubmit | subagentStart |
subagentStop | stop
```

Every input contains the common fields `session_id: string`,
`transcript_path: string|null`, `cwd: string`, `hook_event_name: string`, and
`model: string`. The complete installed event-specific input surface is:

| Event | Additional input fields |
| --- | --- |
| `SessionStart` | `source: startup|resume|clear|compact`; `permission_mode` |
| `SessionEnd` | `reason: other` |
| `SubagentStart` | `turn_id`, `agent_id`, `agent_type`, `permission_mode` |
| `PreToolUse` | `turn_id`, `tool_name`, `tool_use_id`, `tool_input`, `permission_mode` |
| `PermissionRequest` | `turn_id`, `tool_name`, `tool_input`, `permission_mode`; `tool_input.description` may be present |
| `PostToolUse` | `turn_id`, `tool_name`, `tool_use_id`, `tool_input`, `tool_response`, `permission_mode` |
| `PreCompact` | `turn_id`, `trigger: manual|auto` |
| `PostCompact` | `turn_id`, `trigger: manual|auto` |
| `UserPromptSubmit` | `turn_id`, `prompt`, `permission_mode` |
| `SubagentStop` | `turn_id`, `agent_id`, `agent_type`, `agent_transcript_path`, `stop_hook_active`, `last_assistant_message`, `permission_mode` |
| `Stop` | `turn_id`, `stop_hook_active`, `last_assistant_message`, `permission_mode` |

The current [Hooks documentation](https://learn.chatgpt.com/docs/hooks) documents the
same event behavior and explicitly says that Bash and unified exec match as `Bash`.
For both `PreToolUse` and `PostToolUse`, Bash uses `tool_input.command`.
`PostToolUse` additionally has `tool_response`; it does not have `commandActions`, an
access list, or a file-read field. `PostToolUse` also covers a non-zero Bash exit, so a
separate failure event is not needed and `PostToolUseFailure` was not found.

The documentation warns that specialized tool paths can opt out and hooks are not a
complete enforcement boundary. That reinforces the need to describe hooks as lifecycle
signals, not exhaustive filesystem telemetry.

Version sensitivity: published `0.150.1` supports the same eleven events plus
`interrupt`. The official [0.150.0 changelog entry](https://learn.chatgpt.com/docs/changelog)
is the source for the new `Interrupt` hook. It does not change the Bash payload or add
read metadata.

**Finding:** the installed hooks API is richer than the nine configured handlers but not
richer in file-access data. Bash `PostToolUse` cannot be relied on to contain structured
file access in either checked version.

## 3. App-server protocol and passive observation

The app-server is a JSON-RPC service over a local transport. Its documented surface is
grouped around initialization/capability negotiation; thread start, resume, fork, read,
list, pagination, metadata, archive and delete; turn start/steer/interrupt; review;
configuration, account and model discovery; hooks; MCP; filesystem helpers; and streamed
thread, turn, and item lifecycle notifications. Some methods require the
`experimentalApi` capability. The authoritative overview is the
[Codex app-server documentation](https://learn.chatgpt.com/docs/app-server).

Two read paths matter:

- `thread/read {threadId, includeTurns:true}` is documented as reading a stored task by
  ID without resuming it. This is the stable primary path.
- `thread/items/list {threadId, cursor?, limit?, sortDirection?, turnId?}` returns
  paginated `ThreadItemEntry` values and is a more efficient incremental path, but is
  explicitly experimental in the current documentation. It should be capability-detected,
  not required for correctness.

Starting or resuming a task automatically subscribes that connection to live item
events. The public protocol has `thread/unsubscribe` but no attach/subscribe-by-ID method
for a task already owned by another app-server connection. Therefore Stickguy should not
try to attach to the desktop app's private transport. It should launch its own local
app-server child and use read-only persisted-task methods.

### Live desktop compatibility test

I ran the installed binary as a separate process with remote control disabled:

```sh
/Applications/ChatGPT.app/Contents/Resources/codex \
  -c features.remote_control=false app-server --listen stdio://
```

After `initialize`, I sent, with the current task ID substituted locally:

```json
{"method":"thread/read","id":2,
 "params":{"threadId":"<current-desktop-thread-id>","includeTurns":true}}
```

The response returned the still-running ChatGPT desktop task with status `notLoaded`
in the observer process, proving it was read rather than resumed. Completed
`commandExecution` items included path-bearing `commandActions` for simple reads.

I then sent:

```json
{"method":"thread/items/list","id":3,
 "params":{"threadId":"<current-desktop-thread-id>",
           "limit":5,"sortDirection":"desc"}}
```

The installed `0.149` app-server returned the most recent persisted items plus forward
and backward cursors. This demonstrates a passive incremental implementation path, but
because `thread/items/list` is experimental, the stable `thread/read` path must remain
the compatibility baseline.

This process did not issue `thread/start`, `thread/resume`, `turn/start`, a write method,
or an approval response. It was terminated after the read test. No daemon control socket
was present before the test; a private stdio child is therefore the appropriate one-service
architecture for Stickguy.

### Limits

- App-server returns complete item objects, including raw commands and output. Stickguy
  may inspect these locally but must project immediately to validated repository-relative
  paths and fingerprints, then discard raw fields without logging or persistence.
- `commandActions` are best-effort classifications, not system-call evidence.
- Stable `thread/read` can be large. Refresh asynchronously after a hook signal and
  deduplicate by item ID. Use the experimental cursor API only as an optimization.
- A version-matched bundled binary avoids state/schema skew. Decode tagged unions
  tolerantly and fail to empty/unsupported on unknown variants.

**Finding:** the app-server supplies a supported passive route to partial structured
read evidence for ordinary desktop tasks. It does not supply a live attach feed or
exhaustive read tracking.

## 4. OpenAI SDKs and APIs

### Codex SDK

The [Codex SDK documentation](https://learn.chatgpt.com/docs/codex-sdk) says the TypeScript
SDK starts, continues, and resumes local Codex tasks, while the Python SDK controls a
local app-server over JSON-RPC. It is useful when an application owns the Codex run.
Making Stickguy launch or operate user tasks through this SDK would cross the product
boundary into being a coding-agent harness. The read-only app-server method above gets
the relevant benefit without owning the model loop.

### Responses API shell

The [Responses shell documentation](https://developers.openai.com/api/docs/guides/tools-shell)
defines paired `shell_call` and `shell_call_output` items. The first contains commands;
the second contains output and exit outcomes. No accessed-file list is documented. In
local-shell mode the caller owns execution and could instrument its own executor, but
that applies only to hosted/API workflows the caller created. It cannot observe an
already-running ChatGPT desktop task.

### Agents SDK

The [Agents SDK overview](https://developers.openai.com/api/docs/guides/agents) says the
SDK manages its own agent loop and provides traces across model, tool, agent, guardrail,
and handoff calls. Those traces can describe tools the SDK invoked; they are not an
observer interface for Codex desktop shell processes and do not add a file-access list
to a Bash call.

**Finding:** no OpenAI hosted SDK or Responses item supplies actual file reads for a
locally running desktop Codex task. The applicable local surface is Codex app-server,
not Responses or Agents SDK telemetry.

## 5. MCP

The official [Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)
defines MCP as a way to give Codex access to a server's tools and context. Codex can
hook calls to an MCP tool such as `mcp__filesystem__read_file`, and app-server emits a
structured `mcpToolCall` item for such a call. An MCP server therefore sees file paths
only when Codex chooses one of that server's tools and supplies the path as an argument.

No supported mechanism was found for an MCP server to observe ambient host filesystem
access or Bash subprocess reads. Supplying a filesystem read tool would not force Codex
to use it, and trying to route all reads through it would alter agent behavior and fail
the passive constraint. App-server's newer MCP event-stream methods subscribe to named
events supplied by an MCP server; they are not host filesystem audit events.

**Finding:** MCP can report its own tool calls, not reads performed outside those calls.
It is not a solution for current shell-based Codex inspection.

## 6. Other supported mechanisms

No other sanctioned, passive mechanism producing exhaustive read evidence was found.

- `world_state`, sandbox policy, and permission-profile read entries describe allowed
  access, not actual access.
- `fs/watch` and macOS filesystem change notifications concern mutations, not reads.
- Endpoint Security, DTrace/`fs_usage`, interposition, or injected wrappers would be
  privileged, platform-specific, invasive, or unsupported. They also conflict with the
  no-shim/no-CGO and passive product constraints and were not pursued.
- Independent parsing of raw Bash strings is not a vendor contract and is worse than
  consuming Codex's own structured action classifier.

## Ranked recommendation

### 1. Implement a read-only Codex app-server observer

This is the recommended production direction.

- Run one version-matched private app-server child from the per-user Stickguy service.
- Use hooks only as fast, fail-open lifecycle signals. A Bash `PostToolUse` should enqueue
  an asynchronous refresh and return immediately; it should not parse or wait.
- Discover/match tasks with `thread/list` and read persisted items with stable
  `thread/read(includeTurns:true)`.
- When present and validated, use experimental `thread/items/list` cursors to reduce
  repeated payload size. Fall back automatically to `thread/read` if the method is
  rejected or its response shape is unknown.
- Process only completed `commandExecution` items not previously seen. Accept only
  `commandActions.type == "read"` as file-read evidence. Treat `search` and `listFiles`
  separately; they do not prove that a particular file's contract was read.
- Canonicalize locally, require containment in the registered Git repository, fingerprint
  immediately, and discard `command`, `aggregatedOutput`, transcript text, absolute
  paths outside the repository, and all unrecognized fields.
- Mark the evidence `vendor_inferred`, record the source item ID and Codex version, and
  expose partial-fidelity state honestly in findings/UI.

Tradeoffs: this is public-protocol based, passive, cross-desktop compatible, and avoids
maintaining a shell parser. It still misses `unknown` commands and requires local handling
of privacy-sensitive item objects. Stable polling is less efficient than a live feed.

### 2. Ask OpenAI for an explicit read-observation contract

The ideal forward contract is either:

- `fileRead {path}` items based on successful tool/runtime access; or
- `commandActions` included directly in Bash `PostToolUse`; or
- a read-only subscribe method for already-running tasks.

This is the only route to both high fidelity and a simple passive integration. Until it
exists, Stickguy should not claim complete Codex stale-assumption coverage.

### 3. Use rollout `parsed_cmd` only as a temporary compatibility fallback

If an older or unusual desktop build lacks a readable app-server task surface, the
rollout's vendor-produced `parsed_cmd` is preferable to reparsing `command`. It is already
structured and uses the same action model. However, the official hooks documentation
explicitly says transcript format is unstable, and the internal spelling differs from
the public app-server contract. Feature-detect it, isolate it in the Codex adapter, label
it fragile and `vendor_inferred`, and fail to no read evidence when its shape changes.

Tradeoffs: passive and locally available, but undocumented, silently breakable, and still
incomplete. Do not make it the default when app-server works.

### 4. Do not ship an independent general shell parser as the normal path

A separate parser must model quoting, shells, wrappers, substitutions, pipelines, globs,
aliases, scripts, current directories, and tool-specific semantics. It will be wrong in
both directions, expands the privacy-sensitive parsing surface, and duplicates a vendor
classifier that is already available through a supported protocol. If retained for an
experiment, gate it off by default, never send raw commands off-device, and never elevate
its results above heuristic evidence.

## Version and update policy

Optimize for capability and current supported releases, not frozen desktop quirks:

| Runtime | Verified result | Product treatment |
| --- | --- | --- |
| ChatGPT desktop bundled `0.149.0-alpha.4.1` | Stable `thread/read` can read an active desktop task; `commandActions.read.path` present; experimental paginated items work | Compatible, but not the target floor for a future release |
| Published CLI `0.150.1` | Same `CommandAction` union and read APIs; adds `Interrupt` relative to 0.149, no read-event improvement | Current development baseline checked on 2026-08-28 |
| Future Codex | Unknown | Capability-negotiate; tolerate additive fields; reject unknown action variants; require users to update when the public contract/fix is only in a newer app |

For release, define support by successful app-server initialization plus the documented
`thread/list`, `thread/read`, and `commandExecution.commandActions` shapes. Publish a
minimum Codex/ChatGPT desktop version based on the then-current stable release, and tell
users to update rather than preserving rollout parsing indefinitely. Keep the fragile
fallback time-bounded with telemetry that contains only version and capability booleans,
never task content.

Do not hard-code `0.149` behavior merely because it is installed on this machine. It is
useful compatibility evidence; `0.150.1` is the current forward check, and a true future
`fileRead` contract should supersede this design when OpenAI publishes one.

## Security, privacy, and known limits

- No raw command, output, source, diff, transcript, environment value, credential, or
  absolute non-repository path may cross Stickguy's wire boundary.
- The local decoder should be streaming/bounded, must never log complete app-server
  messages, and should apply the mandatory secret classifier before any derived fact is
  queued for sync.
- Repository containment must be checked after symlink-aware canonicalization. Reject
  missing, special, credential-protected, or out-of-project paths.
- An app-server crash, timeout, schema mismatch, unsupported method, or `unknown` action
  must degrade to empty/partial read evidence without blocking Codex.
- This mechanism improves Codex stale-assumption coverage but cannot make it complete.
  Findings derived from it must disclose lower fidelity until OpenAI provides actual
  read-observation events.
